## V2 risk resolutions (R1-R4)

**R1 - key custody.** `grep -rn "private_key.*write|write.*private_key" core scripts --include=*.py` found exactly one textual hit that is NOT a key write: `facts.write_chain_anchor`/`gate_chain_anchor.py::write_anchor_file` write the ANCHOR DICT (`chain_length`, `tip_hash`, `signed_at`, `owner_sig` - a signature, not a key) to disk; the private key itself is never in that payload. Every one of the 13 signing call sites across `scripts/gate_*.py` uses `secrets.token_bytes(32)`, generated in-process, discarded at exit - confirmed by grep, zero exceptions. **Owner decision required, one sentence:** the owner must choose where a real signing key will live - a hardware key (YubiKey/similar), the OS keychain, or an encrypted file - none of which this account can decide or build. **OWNER-GATED.**

**R2 - per-scope key separation.** `core/apex/kernel/capability_tokens.py` contains no signing code of its own - it documents that the REAL enforcement is `ApprovalBook`'s single shared HMAC secret (`issue()`/`approve()`, one secret for every domain and kind) plus, separately, the one shared Ed25519 key used for facts/cards/anchors. **What breaks if either shared key is rotated, one sentence:** every previously-issued-but-unapproved token (HMAC secret) or every previously-signed fact/card/anchor (Ed25519 key) becomes permanently unverifiable against the new key, indistinguishable from a wholesale forgery, because no key-epoch or supersession attestation exists anywhere in this codebase. Not fixed this session - a design decision for the owner.

**R3 - anchor key survival, answered with a test.** Ran two genuinely separate `python3` process invocations (two OS processes, no shared Python state): process 1 generated an ephemeral key, wrote a persona card + one signed fact + a chain anchor, and ALSO persisted the PUBLIC key (safe to persist) to its own file, then exited (private key gone). Process 2, started fresh, loaded only `anchor.json` and the public-key file and called `facts.verify_chain_against_anchor`:
```
PROCESS1 wrote anchor and public key; private_key now goes out of scope
=== PROCESS 1 EXIT - private key is gone, new OS process below has never seen it ===
PROCESS2 (fresh, never had the private key) verify result: {'ok': True, 'reason': None, 'length': 1}
```
**Answer: the anchor is NOT self-referential** - Ed25519 verification genuinely works across a process boundary with no shared state. **But**: no existing `scripts/gate_*.py` script does this today (every one generates and uses its key within a single process), and - the real residual gap - **nothing in this repository authenticates the public-key FILE itself**: `verify_chain_against_anchor` trusts whatever `public_key_bytes` it is handed; there is no pinning, fingerprint display, or out-of-band check that a given `public_key.hex` file is really the owner's. This is a sharper restatement of R1, not a new separate risk: the cryptography is sound, the key-distribution/trust problem is unbuilt.
